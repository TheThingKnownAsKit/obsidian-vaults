## Unit Testing
**Unit testing:** looking for errors in a subsystem in isolation.
* Generally a "subsystem" means a particular class or object
* The Java library JUnit helps us to easily perform unit testing. The tool

For a given class Foo, create another class FooTest to test it, containing various "test case" methods to run. Each one looks for a particular results.

JUnit provides "assert" commands to write tests.
```
public class StringLibrary {
	public String concat(String one, String two) {
		return one + two;
	}
}

public class StringLibraryTest {
	@Test
	public void testConcatWithTwoNonEmptyStrings() {
		String expectedResult = "onetwo";
		String result = myUnit.concat("one", "two");
		assertEquals("Incorrect concatenation.", expectedResult, result);
	}
}
```
Things to note:
* @Test is required. It just tells the program that this is a test function. Enables test functionality that is not enabled by default. It matters that T is capitalized.
* The method name will be really long and really specific
* Create an expected result. You don't have to, but you SHOULD. DO IT.
	* Note: Can be ranges of correct answers. However, if you don't really know what you're looking for, try integration testing. (how multiple functions behave)
* Create the result
* Use assertEquals with an incorrect result message (required)
	* This gets printed in the test window, not printed in the console.

The **happy path** is testing input that should be the most simple way to go through a function. It should be input the function likes.


#### Basic template for writing unit tests
The **SETT** framework: (theres an invisible F at the beginning)
* F stands for Function - choose the one function you're going to test
* S is for Setup - instantiate all variables you'll need in your test
* E is for Execute - execute the function you're testing 
* T is for Test - Did the function do what you expect?
* T is for Tear-down - Do you need to release any resources or undo any side-effects?
	Usually empty. Not common at all.

#### JUnit (4) Assertion Methods
| method                            | utility                                                             |
| --------------------------------- | ------------------------------------------------------------------- |
| assertTrue(test)                  | fails if the boolean test is false                                  |
| assertFalse(test)                 | fails if the boolean test is true                                   |
| assertEquals(expected, actual)    | fails if the values are not equal (by .equals())                    |
| assertNotEquals(expected, actual) | fails if the values are equal (by .equals())                        |
| assertSame(expected, actual)      | fails if the values are not the same (by == only use for reference) |
| assertNotSame(expected, actual)   | fails if the values are the same (by == )                           |
| assertNull(value)                 | fails if the given value is NOT null                                |
| assertNotNull(value)              | fails if the given value is null                                    |
| fail()                            | causes current test to immediately fail (useful for TODO)                                                                    |
Each of these methods can be passed a string to display if it fails. It's always the first parameter. Required in this class.

assertSame/assertNotSame are very uncommon but can be useful when comparing references since you're comparing the MEMORY ADDRESSES.
	If you want to see if an index in a string array changed, use assertNotSame because it's possible an identical string was switched with it, which assertEquals would falsly identify.

Don't use any equals or same on doubles because of the imprecision. If you need to, it'll prompt you for a delta (the amount of acceptable difference). Typically at the end.
